# 后台运营与厂商接入准备

## 范围

保留原用户界面、移动底栏与单次租借押金模式。后台在基础管理之上增加订单详情/筛选、工作队列、关联客服会话、价格版本历史和安全操作差异记录。厂商相关流程通过明确标记的 TEST 联调区演练，不代表真实接入已经完成。

生产部署仍为 Node.js 24 + SQLite 单实例。本轮沿用 schema v4，不迁移或覆盖原用户、订单和支付。新增历史及联调记录存储在现有 records 表的独立 kind 中。升级前仍须备份数据库。

## 运营入口

- Orders：按身份模式、订单信息、状态和日期筛选；详情展示费率快照、押金、费用抵扣、退款、待核查差额、真实记录时间线，以及关联用户、资金记录和客服。
- Work queue：已记录的结算核查和未解决客服事项。没有真实事件支撑时，不生成伪造设备告警。
- Support：新工单可以关联同一用户、同一 TEST/LIVE 模式下的订单。客服回复追加保存，不覆盖旧回复；用户可在原工单继续回复，已解决工单会重新打开。工单解决不代表设备修复或退款到账。
- Pricing：展示规则与版本历史。正式价格不改变 DEMO-001 固定示例价格；成交订单保留原价格快照。
- Audit：最近 200 条操作记录及允许记录的字段变化。不会将密码、令牌、任意供应商报文或客服正文复制到操作差异中。
- Integrations：独立的模拟联调区，展示设备库存、指令/取出状态、支付/退款结果、异常及核查记录。

## 状态必须分开

1. 租借：待付款、待取、使用中、归还、取消等。
2. 资金：押金确认、租金抵扣、退款待处理/成功/失败、待核查等。
3. 设备：未接入、指令状态、取出证据及库存新鲜度。

押金不是营业收入，租金抵扣不是再次收款。设备命令被接收不是充电宝已被取走。退款请求被受理不是退款到账。客服结案及异常备注不修改底层资金或设备事实。

## 权限和数据边界

- owner：原有资料与价格管理、客服处理，以及 TEST 联调。
- operator：客服处理、TEST 联调；不能修改正式站点与计价规则。
- viewer：只读；不能通过直接调用 API 越权写入。
- 所有管理写入仍要求独立管理员会话、同源及 CSRF 校验。
- TEST 客户、正式客户和管理员身份分离；订单关联在服务端核验所有权及模式。
- 联调实验记录与真实资金、机柜、客户 TEST 租借账本分离。实验成功不会改变真实订单或自动开启真实支付/机柜控制。

## 升级后验收

1. 分别检查 owner/operator/viewer，确认只读用户无写权限。
2. 用 TEST 客户完成租借，从历史或收据创建关联工单。
3. 后台按订单找到工单，回复；客户继续回复原工单，确认历史保留且解决状态正确重新打开。
4. 在订单详情核对押金、租金、退款及时间线；客户不能关联别人的订单。
5. 保存新计价并检查版本历史；两处同时编辑时旧版本保存遭拒绝。
6. 在 TEST 联调区逐项演练已付未出宝、取出结果未知、归还未匹配、退款处理中、退款失败及成功。
7. 检查刷新和服务重启后的实验记录仍在；重复请求不产生重复操作；异常备注不能伪装为资金结算成功。
8. 正式 Google/PVS/WsCharge 仍保持未接入或未验证，不能因 TEST 演练通过显示“可营业”。

自动化 API/控制器测试与本地 HTTP 冒烟测试不等于手机相机、视觉适配、真实支付或机柜端到端验收。
